# Module 3 Project: Designing an E-Commerce Application Architecture

## Part 1: Traditional Server Scaling Design
This project designs an e-commerce web application starting with using a traditional three-tier architecture — a web layer, an application layer, and a data layer. Customers browse products, manage accounts and carts, and place orders through the web layer.
The application layer handles business logic — authentication, inventory checks, order management, and payment requests. The data layer stores structured records in Amazon RDS and static assets in Amazon S3. EC2 instances run both the web and application tiers, with Multi-AZ deployment, Elastic Load Balancing, and Auto Scaling for availability and horizontal scaling. CloudFront sits in front to cache and deliver static content faster.

### Scaling strategy
A separate scaling policy and capacity should be defined for each web and application tier. Both tiers should have minimum, desired, and maximum capacity. As a starting point, it is good to have at least two healthy instances per Availability Zone for each tier. Scale horizontally by adding or removing instances as needed. The web tier can use target tracking with metrics such as ALB request count per target and CPU utilization. For an application tier that processes synchronous requests, scaling can be based on CPU utilization or custom metrics such as active requests or concurrency per instance.
Vertical scaling of the RDS database can help meet changing capacity needs, while scaling based on demand can improve cost efficiency by optimizing resource usage. Select an Amazon RDS DB instance class based on the database engine, workload, and expected resource needs. General-purpose M-family classes can provide a balanced baseline and may be a suitable starting point. Monitor database performance to identify resource constraints and capacity needs. Test alternative instance classes in a non-production environment before adopting them, then establish a documented plan for updating the database configuration as requirements evolve. Several instance options can accommodate specific resource requirements—for example, C-family instances for high CPU requirements and R-family instances for higher memory requirements.
### Design Rationale and Security Considerations
A three-tier architecture separates the web, application, and data processes, making each layer’s responsibilities clear. EC2 provides control over the runtime, while separate web and application tiers can scale independently. A load balancer routes requests to healthy instances and provides a stable entry point as instances are added or replaced. RDS can store shared session data and allow instances to access it, though it is generally better suited to structured application data.
The load balancer is the public entry point, and customer traffic uses HTTPS. The EC2 instances and Amazon RDS database are placed in private subnets, with access restricted to the required paths between the load balancer, web tier, application tier, and database. The S3 bucket is configured for private access, with permissions limited to the application or CloudFront as needed. IAM roles should follow the principle of least privilege, and database credentials and payment-service secrets should be stored outside the application code. Additional security measures can build on this design. For example, data should be encrypted in transit and at rest, and the design should include monitoring, backups, and regular patching. 

## Part 2: Serverless Architecture Design
This design uses the same e-commerce application with a serverless architecture. The frontend is hosted in an S3 bucket and delivered through CloudFront. API Gateway routes incoming requests to AWS Lambda functions, which handle product browsing, account management, cart updates, order processing, and payment coordination.
Lambda functions use IAM roles to access Amazon DynamoDB for application data and a separate S3 bucket for assets. EventBridge publishes events that trigger a secondary Lambda for async tasks like order notifications and post-purchase processing. There are no servers to manage; each service scales automatically with demand.

### Scaling strategy
API Gateway throttling and Lambda concurrency are separate controls. API Gateway acts as the front door, and Lambda acts as the worker; both services scale separately.
•	API Gateway admits requests up to its throttling settings. It can also set burst limits to allow temporary traffic spikes.
•	Exceeding the throttling limits will result in API Gateway returning an HTTP 429 (Too Many Requests).
•	Lambda’s provisioned concurrency keeps environments ready. Reserved/account concurrency and available capacity determine how many requests it can handle simultaneously. Increasing reserved concurrency can allow more synchronous Lambda invocations. 
•	Lambda throttles on synchronous calls may appear through API Gateway as a 429 or a 5xx, depending on the API type and integration behavior. 
•	Use SQS to buffer asynchronous work, with a DLQ for repeated failures, and apply bounded exponential-backoff retries with jitter.
DynamoDB capacity mode affects throughput management, while keys and indexes determine how evenly requests are distributed. DynamoDB scaling depends on whether you choose on-demand or provisioned capacity. With on-demand capacity, DynamoDB adjusts capacity with request volume; with provisioned capacity, auto scaling can adjust capacity toward configured targets. Add read replicas only when needed — after monitoring and analysis confirm that read load is exceeding current capacity. Designing partition keys and indexes to spread requests is crucial for well-defined distributed access patterns. 
### Design Rationale and Security Considerations
The storefront is hosted in S3 and delivered through CloudFront, reducing server maintenance and improving load times through edge caching. API Gateway provides a single entry point that routes frontend requests to Lambda functions. Separate, functions handle browsing, accounts, carts, orders, and payments, allowing them to scale and change independently without managing application servers. DynamoDB stores application data and supports fast, high-throughput lookups, such as product and customer cart queries.
Security should be applied throughout the design. Keep S3 buckets private and serve content through CloudFront over HTTPS. Protect API Gateway routes with authentication, request validation, and throttling. Give each Lambda function a dedicated IAM role with only the permissions it needs. Store credentials and payment-provider secrets securely rather than including them in code, and ensure logs do not contain sensitive information. Restrict access to DynamoDB data and encrypt it, ensuring users can access only their own records. Verify payment callbacks, avoid storing raw card details, and make event handlers resilient to retries and duplicate events.

## Part 3: Comparison and Analysis
### Scalability and Cost Considerations
EC2 instances take time to launch, so capacity must be planned ahead. Each tier scales independently, and RDS scaling is separate and may require planned resizing. EC2 charges continue while instances are running, including baseline capacity for availability. Load balancing, storage, data transfer, and RDS add to the cost. This model can suit steady, predictable workloads when capacity is right-sized.
Lambda costs depend on requests, execution time, and memory; API Gateway and DynamoDB costs depend on usage and configuration. This can reduce idle-compute costs compared to EC2, though high traffic, long-running functions, and provisioned concurrency can increase the bill.
The data layer is a key trade-off. The traditional design uses RDS, while the serverless design uses DynamoDB. RDS is suited to relational data, transactions, and complex relationships. DynamoDB works well when access patterns are known and supported by well-designed keys and indexes. If orders, inventory, and payments require relational constraints or complex queries, retaining RDS or using a hybrid architecture may be preferable.
### Development and deployment workflows
Traditional design: Developers use familiar web and application servers, frameworks, and long-running processes. The tiers can share code or be released separately. Initial deployment involves configuring EC2 instances, deploying application code, and setting up load balancing and Auto Scaling. The team also manages instance updates, patching, capacity, session handling, and rollbacks. 
Serverless design: Developers divide the application into functions, such as product browsing, cart updates, and order processing. Initial deployment involves configuring functions, API routes, permissions, and supporting services, often with infrastructure-as-code. Functions can be deployed independently, but teams still need to manage testing, configuration, monitoring, retries, and rollbacks.
### Suitability for various application types
The traditional design is a good fit for long-running applications that rely on relational data, need control over the runtime, or use an existing server-based codebase. The serverless design is a good fit for variable traffic, event-driven tasks, and applications that can be divided into independent APIs or functions. For this e-commerce application, serverless can be a practical starting point if the data and API needs fit DynamoDB and order tasks can run asynchronously. The traditional design may be a better fit if the application needs complex relational transactions or greater control over its runtime. A hybrid approach—such as a serverless frontend with a relational database or containerized application tier—is also an option.
